| 2026-11-11 | `gh` runs outside the sandbox: `sandbox.excludedCommands: ["gh *"]` in `.claude/settings.json` (Dusten, 11 Nov). The entry must end in ` *`: the sandboxing guide ("Format of entries", https://code.claude.com/docs/en/sandboxing.md) reads "entries use the same syntax as a `Bash(...)` permission rule, where a pattern with no wildcard is an exact match. `docker` matches only `docker` with no arguments. `docker *` matches `docker` with or without arguments", so a bare `gh` would leave `gh auth status` sandboxed. The key works from a repo file: the settings reference gives it Scope "Any file" (https://code.claude.com/docs/en/settings-reference.md), unlike `strictAllowlist`; the guide says Claude Code ignores repo entries only "while the sandbox is admin-required", which `allowUnsandboxedCommands: false` in a repo or user file does not cause (managed settings or `--settings` do), and which does not apply here (no managed settings). With `allowUnsandboxedCommands: false`, "commands Claude runs are then sandboxed unless they match an `excludedCommands` entry", so only `gh` is excluded; a test requires the list to equal `["gh *"]`. Deny and ask rules still apply: "An excluded command goes through the regular permission flow". Three denies added because an unsandboxed `gh` could print its token: `Bash(gh auth token*)`, `Bash(gh auth status *--show-token*)`, `Bash(gh auth status *-t*)`. The option-first forms (`Bash(gh * auth token*)` and the like) were dropped: their leading wildcard matched any `gh` command whose text mentioned "auth token", which silently refused `gh pr create` when the title or body said so; a test now rejects any option-first `gh auth` deny. PR text goes in with `--body-file`. Plain `gh auth status` has no argument, so it is not matched; `*-t*` also denies a `gh auth status` call with any argument containing `-t`, accepted. Trade-off: an excluded `gh` has no filesystem or network limits, so it can read `~/.config/gh` and reach any host; the only limits on it are text-matched permission rules, which do not see `bash -c`, a full path or a script that calls `gh`. If managed settings or `--settings` later set `allowUnsandboxedCommands: false`, the repo entry is ignored and must move to `~/.claude/settings.json`. | Inside the sandbox `gh` cannot read its login in `~/.config/gh` (denied as a secret path), so `gh pr` and `gh api` fail. Excluding only `gh` keeps the rest of the sandbox, and the deny and ask rules keep gating every `gh` call. |
