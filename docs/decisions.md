| 2026-11-11 | `gh` runs outside the sandbox: `sandbox.excludedCommands: ["gh *"]` in `.claude/settings.json` (Dusten, 11 Nov). The entry must end in ` *`: the sandboxing guide ("Format of entries", https://code.claude.com/docs/en/sandboxing.md) reads "entries use the same syntax as a `Bash(...)` permission rule, where a pattern with no wildcard is an exact match. `docker` matches only `docker` with no arguments. `docker *` matches `docker` with or without arguments", so a bare `gh` would leave `gh auth status` sandboxed. The key works from a repo file: the settings reference gives it Scope "Any file" (https://code.claude.com/docs/en/settings-reference.md), unlike `strictAllowlist`; the guide says Claude Code ignores repo entries only "while the sandbox is admin-required", which `allowUnsandboxedCommands: false` in a repo or user file does not cause (managed settings or `--settings` do), and which does not apply here (no managed settings). With `allowUnsandboxedCommands: false`, "commands Claude runs are then sandboxed unless they match an `excludedCommands` entry", so only `gh` is excluded; a test requires the list to equal `["gh *"]`. Deny and ask rules still apply: "An excluded command goes through the regular permission flow". Six denies added because an unsandboxed `gh` could print its token: `Bash(gh auth token*)`, `Bash(gh * auth token*)`, `Bash(gh auth status *--show-token*)`, `Bash(gh * auth status *--show-token*)`, `Bash(gh auth status *-t*)`, `Bash(gh * auth status *-t*)`. Plain `gh auth status` has no argument, so it is not matched; `*-t*` also denies a `gh auth status` call with any argument containing `-t`, accepted. Trade-off: an excluded `gh` has no filesystem or network limits, so it can read `~/.config/gh` and reach any host; the only limits on it are text-matched permission rules, which do not see `bash -c`, a full path or a script that calls `gh`. If managed settings or `--settings` later set `allowUnsandboxedCommands: false`, the repo entry is ignored and must move to `~/.claude/settings.json`. | Inside the sandbox `gh` cannot read its login in `~/.config/gh` (denied as a secret path), so `gh pr` and `gh api` fail. Excluding only `gh` keeps the rest of the sandbox, and the deny and ask rules keep gating every `gh` call. |

Docs: code.claude.com settings-reference ("Sandbox settings", "Sandbox path prefixes", `sandbox.network.allowedDomains`), sandboxing ("Configure sandboxing", "Default write and temp locations"), permissions ("Read and Edit"). | The sandbox limits what a shell command can read, write and reach, even when a prompt injection gets past the permission rules. Network access is enforced by `sandbox.network.strictAllowlist` plus `allowedDomains` in each developer's `~/.claude/settings.json` (or managed settings), not by this repo's file. `strictAllowlist` is left out of the repo file (a test asserts it is absent): the settings reference lists it with Scope "User or managed" and the description "Deny hosts outside the allowlist instead of prompting" (https://code.claude.com/docs/en/settings-reference.md#sandbox-network-strictallowlist). The sandboxing guide's locks table ("Locks that apply without an admin-required sandbox", https://code.claude.com/docs/en/sandboxing.md) reads: "`network.strictAllowlist` | Managed settings, `--settings`, user settings | The proxy ports, `allowedDomains`, and `WebFetch(domain:...)` allow rules". So a repo's `allowedDomains` is ignored under strict mode and is kept here only as the record of the hosts this project needs. Network test on 2026-11-11 with `strictAllowlist` true and `allowedDomains` `pypi.org`, `files.pythonhosted.org`, `github.com`, `api.github.com` in `~/.claude/settings.json`: `curl https://pypi.org/simple/` returned 200 (exit 0); `curl https://example.com` failed with `CONNECT tunnel failed, response 403` (exit 56) and the sandbox log `deny network-outbound example.com:443 (host is not on the allow list)`; Python `urlopen('https://example.com')` failed with `Tunnel connection failed: 403 host is not on the allow list` (exit 1) and the same log line; no prompt appeared. `make check` and `make audit` passed inside the sandbox. |
